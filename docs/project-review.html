5. Issues found (prioritized)

5.1 Critical — must fix to run

#IssueWhereWhy it matters
C1 Property name mismatch: controller uses request.SessionId; DTO has ConversationId. ChatController.cs, ChatRequest.cs Build fails. Pick one name everywhere (recommend SessionId or ConversationId consistently).
C2 Streaming over HTTP is incorrect: returns Ok(stream) which serializes poorly; clients won’t get true SSE/chunked token stream. ChatController.cs Quickstart teaching point is streaming UX. API needs Results.Stream / SSE / NDJSON, not JSON-wrapping an IAsyncEnumerable naively.

5.2 High — correctness & product fit

#IssueWhereWhy it matters
H1 System prompt is generic, not an AI librarian. PromptBuilder.cs Quickstart’s main lesson: persona + instructions drive useful answers. For AI Library: catalog help, recommendations, citations, ask for genre/age/reading level, etc.
H2 No input validation on message/session (null/empty). DTO + controller/handler Nullable disabled in Application; empty messages still hit the model and pollute history.
H3 History list is not thread-safe per session. ChatHistoryStore + handler Dictionary is concurrent; List<ChatMessage> is not. Parallel requests same session can corrupt history.
H4 History grows forever (no trim / token budget). handler / store Long chats exceed context window; cost/latency explode. Quickstart ignores this; real apps must cap or summarize.
H5 Duplicate / dead types: IConversationStore + empty InMemoryConversationStore vs real IChatHistoryStore. Application + Infrastructure Confusing for learning; remove or finish one design.
H6 Placeholder Class1.cs in Domain/Application/Infrastructure. multiple Noise; delete once real types exist.
H7 WeatherForecast sample leftover in Program.cs. Program.cs Unrelated to AI Library; remove to keep mental model clean.

5.3 Medium — quality, security, maintainability

#IssueWhy
M1 Inconsistent namespaces / missing file-scoped consistency: some types public without matching folder namespace style; controller namespace declared but class not nested consistently. Harder navigation and discoverability.
M2 Nullable inconsistency: Application has <Nullable>disable</Nullable>; other projects enable it. Hides null bugs; align all projects to enable.
M3 Ollama package is preview 9.7 while Microsoft.Extensions.AI is 10.8.3. Version skew risk. Prefer matching MEAI.Ollama / current docs package set, or switch to OpenAI package when you follow the OpenAI pivot exactly.
M4 Config nullability: no guard if Ollama:Endpoint / Model missing. Fails late with unclear errors.
M5 No CORS, auth, rate limiting. Fine for local learning; needed before any public client.
M6 ChatResponse DTO unused. Either use for non-streaming endpoint or remove.
M7 OpenAPI vulnerability warning. Bump package versions when fixing restore.
M8 No README / no run instructions (Ollama must be running, model pulled). You (and future you) will forget setup steps.
M9 HttpsRedirection after MapControllers order is odd; middleware order should be intentional. Pipeline clarity.
M10 MediatR returning IAsyncEnumerable is awkward (Task.FromResult of async stream). Works but harder to test/cancel; consider streaming endpoint calling IChatService directly, or a dedicated streaming pipeline.

5.4 Low — polish

  • Empty folders: Api Extensions/Middlewares/Configuration, client/, .github/.
  • No .editorconfig / Directory.Build.props for shared settings.
  • No integration test that hits chat with a fake IChatClient.
  • MaxOutputTokens fixed at 400 — OK for learning; make configurable later.

6. Alignment with “AI-powered library” idea

Today the app is a generic chat API over Ollama. It is not yet a library product. To turn the quickstart into your idea, treat chat as the interface and the library as the domain + tools.

Suggested product vision (learning-friendly MVP)
  1. Librarian chat — system prompt: recommend books, explain genres, help find titles, ask clarifying questions (age, interests, length).
  2. Catalog data — Domain entities: Book, Author, Genre; seed a small in-memory or SQLite catalog.
  3. RAG later — embed book blurbs/reviews; retrieve top-k before answering (next Microsoft Learn AI modules often cover this).
  4. Tools / function calling — “search catalog”, “get book by ISBN” as AI tools so answers are grounded.
  5. Simple client — minimal Blazor/React/HTML page that streams tokens (mirrors console loop from quickstart).

Why this order: You solidify quickstart skills (IChatClient, history, system prompt, streaming) first, then add domain value without jumping straight into vector DBs.

8. Concrete code notes (for when you fix)

8.1 Session id mismatch (C1)

// ChatRequest today
public string Message { get; set; }
public string ConversationId { get; set; }

// ChatController today (broken)
new ChatCommand(request.SessionId, request.Message)

Either rename DTO → SessionId, or pass request.ConversationId. Keep command, store, and API contract identical.

8.2 Quickstart-style library system prompt (H1)

You are a friendly librarian assistant for an AI-powered library.
Introduce yourself when the user first says hello.
Before recommending books, ask for:
1) preferred genres or topics
2) age group or reading level
3) approximate book length or time available
Suggest up to three titles with a one-sentence why.
If you are unsure a title exists in the catalog, say so.
End by asking if they want more options or a different genre.

Why: Same teaching pattern as the hiking prompt — role, required inputs, structured output, polite closing.

8.3 Provider swap (learning MEAI)

Today:

services.AddSingleton<IChatClient>(_ =>
    new OllamaChatClient(
        new Uri(configuration["Ollama:Endpoint"]),
        configuration["Ollama:Model"]));

OpenAI pivot (conceptually, from the Learn page):

new OpenAIClient(key).GetChatClient(model).AsIChatClient();

Why: Application/handler code should not care which provider is registered — that is the core Microsoft.Extensions.AI lesson.
